# Testing

> Framework-agnostic reference conventions. Adjust to the project's actual test tool
> (pytest, vitest, jest, cargo test...) when starting. The `tdd` skill drives the red → green
> loop; this file is the reference it consults for what to test and how.

## What to test

- Non-trivial business logic and new endpoints/routes — always.
- Reusable utilities (helpers, parsers, validators) — always.
- Bugfixes: add the test that reproduces the bug before fixing it, so it stays as a regression test.
- Don't test trivial getters/setters or generated code (migrations, autogenerated types).

## How

- **Isolate**: every test must be able to run alone and in any order. No shared state between tests except explicit fixtures.
- **Don't over-mock**: mock real external boundaries (network, filesystem, third-party services), not the project's own internal layers — if you mock too much, the test stops proving anything.
- **Name by behavior**, not by implementation: `test_rejects_duplicate_email`, not `test_function_2`.
- **Arrange-Act-Assert**: structure each test as prepare, execute, verify; avoid conditional logic inside the test.
- **One conceptual assert per test** — several `assert`s are fine if they verify the same claim from different angles; if they check unrelated things, split them.

## Before calling a feature done

- Don't report the suite green from memory — run it now and read the output (`verification-before-completion` skill).
- Run the full suite, not just the new tests — a change can break something you didn't touch directly.
- If the project measures coverage, don't chase 100% — chase having the logic with branches/edge cases covered.

## What NOT to consolidate

Before merging tests that look similar, confirm they really cover the same case.
Two tests with a similar structure but that exercise different domains or edge cases must
stay separate even if the code looks repeated — duplication in tests is cheaper than a
false positive in coverage.
